# План улучшения проекта Queue Manager

Дата составления: 2026-10-16

## Краткий результат аудита

- `workers/worker-manager.py` запускает процессы через `nohup` и shell-редирект `> ... 2>&1`. Это сохраняет stdout/stderr, но не является полноценным логированием: нет единого формата записей, ротации, уровня логирования, traceback и отдельной обработки падения процесса.
- Большинство worker-скриптов используют `print()` и локальные `except Exception`; часть исключений только выводится, а часть приводит к отправке ошибки в очередь. При этом общий контекст задачи, имя воркера и PID не фиксируются системно.
- В `config.py` отсутствуют параметры SMTP и флаг включения уведомлений. Файла `.env` в репозитории нет, поэтому секреты в план не включаются и должны задаваться только в окружении.
- `workers/worker-manager.py` и `workers/worker-manager.sh` содержат разные списки воркеров, очередей и количества процессов. Это может приводить к запуску не тех процессов в зависимости от выбранного менеджера.
- В `utils/queue_manager.py` сетевые ошибки и ошибки отправки результата выводятся через `print()`, поэтому они не попадают в единый лог и не позволяют надежно отличить ошибку воркера от временной ошибки API.
- В проекте есть тесты API и утилит, но нет тестов для worker manager, конфигурации SMTP, записи traceback и отправки уведомлений.

## Приоритеты

### P0 — обязательно для надежной эксплуатации

#### 1. Централизованное логирование worker-процессов

**Цель:** при любой ошибке иметь в файле подробную запись, по которой можно восстановить ход обработки.

**Что сделать:**

1. Создать общий модуль, например `utils/worker_logging.py`, с функцией настройки логгера:
   - `RotatingFileHandler` или `TimedRotatingFileHandler`;
   - UTF-8 и единый формат: время, уровень, имя воркера, PID, UUID задачи;
   - отдельный файл на воркер либо единый `logs/workers.log` — выбрать один вариант и документировать его;
   - ограничение размера/срока хранения и количества backup-файлов;
   - `logger.exception(...)` для traceback, а не только текст `str(e)`.
2. В `worker-manager.py` отказаться от shell-строки с `>`, `2>&1` и `&`. Запускать процесс через `subprocess.Popen` с явными `stdout`/`stderr`, проверкой PID и сохранением дескрипторов лог-файлов.
3. Логировать жизненный цикл процесса: запуск, PID, остановку, ненулевой exit code, неожиданное завершение и повторный запуск.
4. Вынести логирование из worker-скриптов и `utils/queue_manager.py` из `print()` в общий logger. В местах обработки задач добавлять `task_uuid`/`queue_uuid` через `LoggerAdapter` или context filter.
5. Не писать в логи SMTP-пароль, API-ключи, токены и полные URL с секретами.

**Критерии готовности:**

- искусственно вызванное исключение записывает traceback в лог;
- падение subprocess с ненулевым кодом содержит имя воркера, PID и код завершения;
- логи ротируются и не растут бесконечно;
- после перезапуска менеджера старые записи не затираются.

#### 2. Email-уведомления об ошибке через SMTP

**Цель:** отправлять уведомление, если конкретный worker завершил обработку с ошибкой или сам процесс аварийно завершился, но только при явном включении в `.env`.

**Расширить `config.py` параметрами:**

```env
WORKER_ERROR_EMAIL_ENABLED=false
SMTP_HOST=
SMTP_PORT=587
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_USE_TLS=true
SMTP_USE_SSL=false
SMTP_FROM=
SMTP_TO=
```

Названия можно скорректировать под принятую в проекте схему именования, но значения должны быть типизированы (`bool`, `int`, `str`) и валидироваться. `SMTP_TO` лучше поддержать как список адресов через запятую.

**Что реализовать:**

1. Создать отдельный модуль, например `utils/worker_notifications.py`, с функцией `send_worker_error_notification(...)` на стандартной библиотеке `smtplib` и `email.message.EmailMessage`; дополнительная SMTP-зависимость не требуется.
2. Перед отправкой проверять флаг `WORKER_ERROR_EMAIL_ENABLED`. Если он выключен — не подключаться к SMTP.
3. Если флаг включен, но обязательные настройки отсутствуют, записывать понятную ошибку конфигурации в лог и не допускать падения worker manager из-за попытки уведомления.
4. В письмо включать: имя воркера, PID, время, UUID задачи/очереди при наличии, тип ошибки, exit code, последние строки лога и путь к полному лог-файлу. Секреты исключить.
5. Отправку делать в отдельном потоке/очереди уведомлений либо с коротким timeout, чтобы недоступный SMTP не блокировал обработку очереди.
6. Защититься от email-штормов: cooldown/deduplication по воркеру и типу ошибки, например не более одного письма за N минут; отдельное письмо после восстановления можно добавить позже.
7. Ошибку самой отправки email логировать отдельно, но не пытаться бесконечно отправлять уведомление о невозможности отправить уведомление.

**Точки вызова:**

- `worker-manager.py`: аварийное завершение процесса и ненулевой exit code;
- общий worker wrapper/entrypoint: необработанное исключение в процессе;
- обработчик задачи: ошибка обработки, если она не была успешно передана через `send_queue_error`.

**Критерии готовности:**

- при `WORKER_ERROR_EMAIL_ENABLED=false` SMTP-соединение не создается;
- при включенном флаге письмо уходит через TLS/SSL согласно конфигурации;
- ошибка SMTP не завершает менеджер и сама попадает в лог;
- тесты подтверждают маскирование пароля и отсутствие повторной отправки в рамках cooldown.

#### 3. Единый жизненный цикл ошибок задачи

1. Определить классификацию: ошибка входных данных, временная ошибка внешнего сервиса, ошибка subprocess, необработанное исключение, ошибка отправки результата.
2. Для каждой ошибки гарантировать один вызов `send_queue_error` с безопасным сообщением для пользователя и подробностями только в лог.
3. Проверять `returncode` у всех вызовов `subprocess.run`, а также наличие ожидаемого выходного файла.
4. Сохранить исходную причину через `logger.exception` и не терять traceback из-за широких `except Exception`.
5. Не считать ошибкой штатное завершение по `SIGTERM` при команде `stop`.

### P1 — высокий приоритет

#### 4. Устранить дублирование менеджеров воркеров

- Выбрать `worker-manager.py` основным менеджером.
- Перенести списки воркеров, очередей и количества процессов из кода в конфигурацию (например, YAML/JSON или отдельные переменные окружения).
- Обновить Bash-скрипт до thin-wrapper, вызывающего Python-менеджер, либо явно пометить его deprecated.
- Добавить проверку согласованности длин списков и существования файлов воркеров до запуска.
- Перейти от поиска всех процессов `pidof python` к PID-файлам/`Popen`-объектам или точному поиску по command line, чтобы не затрагивать чужие Python-процессы.

#### 5. Надежность сетевого взаимодействия с Queue Manager

- Заменить `print()` в `utils/queue_manager.py` на общий logger.
- Использовать `response.raise_for_status()`/явную проверку статусов и безопасный разбор JSON.
- Ввести backoff с jitter, ограничение общего времени retry и отдельные таймауты connect/read.
- Разделить временные ошибки, окончательные 4xx и ошибки валидации ответа.
- Добавить correlation ID в запросы и записи логов.

#### 6. Конфигурация и безопасность

- Добавить `.env.example` без секретов с описанием всех обязательных переменных.
- Проверять production-конфигурацию при старте и завершать запуск с понятной ошибкой при отсутствии критичных значений.
- Перевести `ws_enabled` со строки на `bool`.
- Убрать hardcoded домены, UUID очередей, абсолютные пути и тестовые значения email из исходников.
- Убедиться, что `.env`, логи, базы и пользовательские файлы находятся в `.gitignore`.
- Проверить права на каталог логов и запретить запись секретных данных в traceback/параметры subprocess.

### P2 — средний приоритет

#### 7. Тестирование и наблюдаемость

- Добавить unit-тесты для `Settings` и разбора SMTP-конфигурации.
- Добавить тесты worker manager с mock для `Popen`, `psutil` и SMTP:
  - успешный старт;
  - ненулевой exit code;
  - необработанное исключение;
  - отключенные уведомления;
  - SMTP timeout и ошибка авторизации;
  - cooldown уведомлений.
- Добавить интеграционный тест с временным каталогом логов и проверкой traceback.
- Добавить health/status-команду с возрастом последнего heartbeat каждого воркера.
- Рассмотреть JSON-логи и экспорт метрик: запущено, перезапущено, ошибок, длительность обработки, размер очереди.

#### 8. Управление ресурсами и очистка

- Гарантировать закрытие файловых дескрипторов при остановке и перезапуске.
- Реализовать корректное завершение: `SIGTERM`, grace period, затем `SIGKILL` при необходимости.
- Централизовать очистку временных файлов и задокументировать сроки хранения.
- Контролировать потребление GPU/CPU и не запускать новые экземпляры при нехватке ресурсов.

#### 9. Документация и эксплуатация

- Обновить `README.md` и `workers/README.md`: установка, запуск, структура логов, настройка SMTP, диагностика.
- Добавить пример systemd/supervisor-конфигурации с stdout/stderr и restart policy.
- Описать runbook: что проверять при падении воркера, где искать лог, как временно отключить email и как проверить SMTP.

## Рекомендуемый порядок реализации

1. Общий logger и ротация файлов.
2. Безопасный запуск/контроль subprocess в `worker-manager.py`.
3. Общий wrapper для необработанных ошибок worker-скриптов.
4. SMTP-конфигурация и модуль уведомлений.
5. Интеграция уведомлений с exit code и ошибками задач.
6. Устранение расхождений Python/Bash manager.
7. Тесты, `.env.example`, документация и эксплуатационные метрики.

## Definition of Done для P0

- Логирование и email можно включить/выключить только конфигурацией `.env` без изменения кода.
- Ошибка любого worker-процесса оставляет структурированную запись с traceback или exit code.
- При включенном и корректно настроенном SMTP администратор получает одно понятное уведомление без секретов.
- Недоступный SMTP не останавливает worker manager.
- Логи ротируются, тесты проходят, инструкция по настройке и диагностике добавлена в документацию.
